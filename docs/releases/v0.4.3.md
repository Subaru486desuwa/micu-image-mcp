# micu-image-mcp v0.4.3: Flare Images API request fix

## Fix

- Fixes default Flare generation failing with HTTP 400, Unknown parameter: response_format. Both generation JSON and edit multipart requests omit this unsupported field for Flare.
- All four image tools use the Images API only. No Responses API or chat-completions fallback is introduced.
- Flare saves backend-selected base64 or URL results. Download and parsing failures no longer regenerate the same image merely to change response format. Other models retain their format selection and fallback.
- The offline HTTP fixture now rejects unsupported Flare fields and non-Images endpoints instead of accepting any payload. Regression tests cover default/legacy IDs, all four tools, explicit configuration, output failures, and legacy-model compatibility.

## Validation

The bounded live entry is the existing Rust example with MICU_RUN_LIVE_TESTS=1 and MICU_LIVE_QUICK_IMAGES=1. It prompts for the API key without echo, starts the selected Rust binary, requests one image with the default Flare model, restarts MCP, and edits that image through its session. Its loopback relay allows only the two Images endpoints, limits upstream requests to two, and records status and response_format presence without credentials.

On 2026-10-16 in Osaka, the v0.4.3 Release candidate completed both live calls against Micu's main endpoint. Default Flare generation returned HTTP 200 in 12.5 seconds; the edit after restarting MCP returned HTTP 200 in 17.2 seconds. Both images were 1024×1024, both requests omitted response_format and quality, and visual inspection confirmed that the blue cup became yellow while keeping its composition. No Responses API requests were permitted by the relay.

## Upgrade

Replace the executable your client actually starts and reconnect MCP. Confirm version 0.4.3 in server_info. Existing configuration, credentials, images, and editing sessions are preserved.
